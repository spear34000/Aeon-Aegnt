| D17 | Skills: who makes them and what format. | **Decided by the owner (2026-11-13): the agent makes skills; the owner does not write them by hand. Skills follow the Agent Skills specification (agentskills.io).** A skill is `<config dir>/skills/<name>/SKILL.md` with front matter `name` (equal to the folder), `description`, optional `license`, `compatibility`, `metadata`, `allowed-tools`, then Markdown instructions; `references/` and `assets/` may hold files. The agent has `skill.create` and `skill.update` (always ask: the owner reads the full text first) and `skill.read` (automatic: the text was approved). Only names and descriptions are in the system prompt; the body is read on demand (progressive disclosure). Text from `skill.read` is handed to the model as instructions, not as untrusted data; that is safe only because nothing writes skills except the owner and an approved `skill.create`, and a skill cannot widen what needs approval (`allowed-tools` is kept but ignored). The agent itself never adds `scripts/`. **Amended by D20:** skills can also be installed by the owner from GitHub or a folder, and installed `scripts/` can run, only in the Docker sandbox after approval. |

| D18 | Provider catalogue and per-device rights. (1) Providers and models are read from models.dev at run time (same source as opencode); base URLs for providers it lists with a dedicated SDK are in code and were only probed, not used with real keys. (2) Keys from other devices are sealed to a server key; (3) devices can be limited to chat and approvals. Replaces "settings only from the PC" for devices the owner trusts. | **Applied, awaiting your confirmation.** Real-model calls through catalogue providers are unverified. |
| D20 | Skills from outside, in two scopes, with scripts. The owner asked for a system compatible with the Agent Skills standard that can find, install and manage skills from folders and GitHub, keep them per user and per project, load them progressively, support `references/`, `assets/` and `scripts/`, version them, and restrict paths and execution. | **Decided by the owner (2026-11-13), with one deviation noted below.** (1) **Trust:** a skill is given to the model only when `skills-lock.json` (in the config folder, outside every workspace) records a hash of exactly its content (SKILL.md plus every file in `references/`, `assets/`, `scripts/`) and it is switched on. A skill that merely appears in a folder (for example with a cloned repository) is listed as `untracked`; one changed after approval is `modified`; neither is offered or readable until the owner approves it again. Skills already in the owner's folder when the lock file first appears are adopted once. (2) **Scopes:** owner skills in `<config dir>/skills`, project skills in `<workspace>/.agents/skills` (the folder other agent clients use); a project skill hides an owner skill of the same name. (3) **Sources:** `owner/repo[/path][@ref]`, a github.com URL, or a folder on the machine; only `codeload.github.com` over HTTPS is contacted, no tokens, no private repositories, at most 10 MB packed, 25 MB unpacked, 1000 files; links and paths that leave the folder are dropped. Installing is the owner's act (admin device): the whole SKILL.md and every script are shown first; the same name is never overwritten silently (rename, which rewrites `name`, or replace); the lock records source, commit and hash; updates are looked for on request and shown as a file diff. (4) **Scripts:** `skill.run` runs a script only inside the Docker sandbox of D7 (no network, read-only root, capabilities dropped, memory/CPU/process limits), after the owner reads the script on the approval card, every time, from a copy of the approved bytes mounted read-only at `/skill`; the workspace is not visible. The agent cannot add scripts. Docker needs to be installed, so it does not work inside the phone app; running on the computer itself is D21. | Reuses ideas from vercel-labs/skills (source forms, content hash, lock, `.agents/skills`, download limits), agentskills.io and the WebMCP SDK (spec rules, unknown fields, link extraction), opencode (directories, last source wins) and deepagents (progressive disclosure, scripts need a sandbox); read from their documentation, no code copied, nothing added to the dependency list. |
| D21 | Skill scripts on the computer itself. D7 said commands run only in the Docker sandbox. The owner (2026-11-13, "ㅇㅇ ㄱㄱ" to the question whether to reverse D7 for this) allowed running skill scripts directly on the computer, with approval every time and restricted execution. | **D7 is reversed only for `skill.run`, and only when a task asks for `isolation: "host"`; there is still no general host-command tool, and Docker stays the default.** Per run: the owner reads the whole script and an isolation sentence on the approval card; the script runs from a fresh copy of the bytes the lock file approved, in a fresh scratch folder that is deleted afterwards; the environment is emptied (no keys or variables of the owner; only PATH and a scratch HOME/TEMP); no shell; 60 s limit; output capped at 200 KB; arguments are single-line and shown quoted. **JavaScript** runs under Node's permission model, configured so it reads only the skill copy and the scratch folder, writes only the scratch folder and starts no programs (Node 20 or later). **That is a safety net against mistakes, not a boundary against hostile code, as Node itself says; symlink bypasses were fixed in later Node releases and the exact fixed version was not checked; the network is not blocked**. **Python and shell scripts have no isolation** besides the limits above and the card says so ("Isolation: NONE"). Not available inside the phone app. The file tools of the agent can no longer touch `.agents/` (project skills live there). Only a runtime option switches host runs off (`hostRunner: null`); there is no setting for it in the apps yet. | A skill the owner approved can still do anything its isolation allows; for Python and shell that is anything the owner can do. The owner is the safeguard there, which is why the script text is on the card. |

The owner wants the UI to work when the server lives on the phone and the app uses it directly. | **Decided and built (results at the end).** Earlier: **Open.** Done so far: the screens say where the agent runs (`이 기기에서 실행` when the server address is this device's loopback, `다른 기기에서 실행` otherwise) and nothing else about the UI assumes a PC. Not tried; it needs about 60 MB of nodejs-mobile plus the NDK as downloads.
