## Open

| ID | Question | Status |
|---|---|---|
| D10 | Secret redaction on tool output is generic (token/password patterns). A config file containing `password: ...` is returned to the model as `[REDACTED]`; if the model writes that file back it is corrupted. Disabling redaction instead sends such secrets to the (possibly external) model. Which do you prefer: (A) keep redaction and block rewriting files that contained redactions, (B) keep redaction as-is and document it, (C) per-path allow/deny lists for redaction? | **Open.** Current behaviour is B. Recommendation: A. |

| D14 | How Aeon runs MCP tools. (A) remote HTTPS servers only, own minimal client (keeps zero runtime dependencies), every call goes through approval; (B) add the official MCP SDK as a dependency; (C) also run package servers (npx/uvx) on the host, which conflicts with D7. | **Open.** Today servers are stored and listed, not executed. Recommendation: A. |
| D15 | Who may add or remove a connection. (A) only the machine running Aeon (current, same rule as providers); (B) any paired device. | **Open.** Current behaviour is A. Recommendation: A. |
| D16 | Outbound requests for the catalogue and logos (registry search, Simple Icons via jsDelivr, publisher sites, GitHub avatars), and showing a brand's mark on community servers named after it. (A) on by default (current); (B) on, with a switch to turn it off; (C) only icons the publisher declared. | **B applied, awaiting your confirmation.** `config.onlineLookups` turns them off; the first-run terms screen asks (optional, off unless chosen) and 내 에이전트 › 약관·권한 changes it. A server that was never asked keeps them on. |
| D17 | Skills: who makes them and what format. | **Decided by the owner (2026-11-13): the agent makes skills; the owner does not write them by hand. Skills follow the Agent Skills specification (agentskills.io).** A skill is `<config dir>/skills/<name>/SKILL.md` with front matter `name` (equal to the folder), `description`, optional `license`, `compatibility`, `metadata`, `allowed-tools`, then Markdown instructions; `references/` and `assets/` may hold files. The agent has `skill.create` and `skill.update` (always ask: the owner reads the full text first) and `skill.read` (automatic: the text was approved). Only names and descriptions are in the system prompt; the body is read on demand (progressive disclosure). Text from `skill.read` is handed to the model as instructions, not as untrusted data; that is safe only because nothing writes skills except the owner and an approved `skill.create`, and a skill cannot widen what needs approval (`allowed-tools` is kept but ignored). `scripts/` are not accepted (Aeon runs no skill code). No remote source of skills is used. |

| D18 | Provider catalogue and per-device rights. (1) Providers and models are read from models.dev at run time (same source as opencode); base URLs for providers it lists with a dedicated SDK are in code and were only probed, not used with real keys. (2) Keys from other devices are sealed to a server key; (3) devices can be limited to chat and approvals. Replaces "settings only from the PC" for devices the owner trusts. | **Applied, awaiting your confirmation.** Real-model calls through catalogue providers are unverified. |
| D19 | Running the agent on the phone itself. The owner wants the UI to work when the server lives on the phone and the app uses it directly. | **Open.** Done so far: the screens say where the agent runs (`이 기기에서 실행` when the server address is this device's loopback, `다른 기기에서 실행` otherwise) and nothing else about the UI assumes a PC. Not done: any way to run the core on Android. Options: (A) embed a Node runtime for Android in the app and ship the TypeScript core (reuses everything, but needs a spike: Node 24 type stripping, `node:sqlite`, APK size, background limits); (B) port the core to Kotlin (one app, a second implementation to keep in step with `src/core`); (C) keep the PC as the only host; (D) the owner runs `aeon serve` in an Android terminal app and the app finds it at `127.0.0.1` (no app work, unverified that Node 24 runs there). Recommendation: D to try the UI now, a one-day spike on A before choosing between A and B. First-run would then add a choice (`이 기기에서 바로 쓰기` / `내 컴퓨터에 연결`, mockup board 처음 연결 · 실행 위치) and, for an in-process server, pairing with no code or QR. | **Spike findings (2026-11-13), read from sources, nothing run on a phone:** the core needs Node 24 only for `node:sqlite` (one file, `sqlite-store.ts`), type stripping and `AbortSignal.any`; everything else is standard modules. nodejs-mobile's latest release is v18.20.4 (2024-10-07, Node 18, `libnode.so` for armeabi-v7a, arm64-v8a, x86_64 plus headers); a Node 22 upgrade is only a pull request whose state could not be confirmed. Using it in a plain Android app needs the NDK and a JNI shim that calls `node::Start` (no NDK is installed here, no native sample was found). Node itself says Android is not a supported platform (BUILDING.md). So (A) is a real but unfinished route: replace `sqlite-store` with a file-backed Store (the store conformance tests exist), polyfill `AbortSignal.any`, emit JS with `tsc` (already a dev dependency), run on Node 18. Not tried; it needs about 60 MB of nodejs-mobile plus the NDK as downloads.
