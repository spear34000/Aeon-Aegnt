# Threat model (Phase 1, single machine)

Assets: the owner's files in the workspace, API keys, prompts/data sent to model providers, the task database.
Trust boundary: only the owner (CLI) is trusted. Models, files read, web pages, tool output, and model-proposed success criteria are untrusted.

| Threat | Mitigation in code | Residual risk |
|---|---|---|
| Prompt injection via file / web / tool output | Output wrapped as untrusted data; permissions decided in code (policy, approvals), not by text; injection heuristics only raise an audit flag | A model can still be *misled* within permitted actions (e.g. write wrong content to an allowed file). Real-model resistance is unmeasured |
| Agent escapes the workspace | `WorkspaceGuard`: `..`, absolute paths, drive switches, symlinks/junctions (realpath of nearest ancestor), `.aeon/` and `.git/` protected | TOCTOU between check and use by another local process |
| SSRF / reaching local services | URL checks, DNS resolution check, redirect re-validation, size/time caps; private, loopback, link-local, metadata ranges blocked | DNS rebinding between the resolve check and the connect; no egress firewall |
| Command execution | Only `sandbox.exec`: allow-listed images, argv (no shell), `--network none`, read-only root, dropped caps, no-new-privileges, memory/CPU/pid limits, per-task scratch mount; always needs approval by default | Docker daemon / kernel escapes; allowed images are pulled by Docker over the network; real Docker path untested here |
| Approval abuse (approve X, run Y) | Approval is bound to a hash of task + step + tool + exact args; the chosen action is persisted so it cannot change after approval; expiry 24 h; late approval refused | The summary shown must be understood by the owner |
| Secret leakage | Keys from env or the platform store (DPAPI / Secret Service / 0600 file), passed to helper processes over stdin, never argv; exact-value + pattern redaction on state, audit, errors, prompts; keys never in URLs | Linux 0600 fallback is not encrypted; same-user malware can use DPAPI-protected secrets; secrets in unrecognised formats; **redaction can corrupt files** the agent reads and rewrites (D10). Prompts sent to external providers contain whatever the agent read |
| Data sent to third parties | External providers require explicit `--consent`; fallback only to consented providers and only if the owner enabled it | EXAONE API terms say usage metadata is always collected and input/output may be used for training depending on consent settings; terms and privacy policy wording conflict (see research notes) |
| Duplicate / zombie execution | Lease + fencing; effect journal; persisted pending action | External side effects are at-least-once; a crash between effect and journal write can repeat it |
| Runaway cost / loops | Step budget, retry cap, local daily call/token budgets, quota waits | Free tiers can change or end; app-level limits do not guarantee a $0 bill on paid clouds |
| Rogue device / LAN attacker | ECDSA device keys; one-time 80-bit pairing codes (16 characters, 5-attempt lockout) (never sent; HMAC proofs both ways); signed requests with 60 s freshness and nonce replay cache; revocation; loopback-only by default; API keys and pairing codes cross the network only sealed to a server key the device pinned while pairing (ECDH P-256 + AES-256-GCM), plain values from loopback only; per-device right to change settings, keys, connections and devices (a limited device keeps chat and approvals) | Plain HTTP on a LAN is not encrypted: eavesdroppers can read task data and the profile (not forge requests, keys or codes); a device with the right to change settings has full control, including pointing prompts at another provider; pairing codes shown on a screen can be read over the shoulder |
| Phone left unattended or stolen | Per-device revocation from any device with the right to manage devices; the background check's notification shows only a count, never what is waiting | An unlocked phone can approve actions and, if it has the right, change settings until it is revoked |
| DNS rebinding / SSRF via redirects, IPv6 tricks | Connect-time address validation, GET-only redirects with per-hop checks, IPv4 embedded in IPv6 (mapped, NAT64, 6to4) and non-global ranges blocked | No egress firewall; OS-level resolver behaviour |
| Data exfiltration via "read-only" network calls | URLs with a query/fragment, and any network request after the task has read workspace content, need approval; model-proposed `http_status` criteria are rejected | Content the owner approves, or path-encoded data in a plain GET before any file was read |
| Windows path aliasing to protected dirs | Canonical (realpath) comparison, trailing dot/space, `::$DATA` and `~N` segments rejected | Other filesystem quirks not yet enumerated |
| Hostile or mistyped server address during pairing | The UI stops polling, signs nothing for the new address until the server proves it knew the pairing code, and restores the old session on failure (tested against a hostile server) | Requests are not bound to the server host, so a request misdirected by other means could be replayed to the real server within its 60 s window |
| Hostile `aeon://pair` link (QR, web page, another app on the phone) | A link only fills in the connect screen: nothing is sent until the owner taps connect, and it is refused on a device that is already paired. Every part is validated (http(s) origin only, no credentials, path or query; at most four addresses; code must be 16 base32 characters) and the address being filled in is named on screen. Probing the addresses (`GET /v1/hello`) only starts after the terms are accepted and only for home or office network addresses (private ranges, 100.64/10, loopback, `.local`) | A link can still suggest an address on the owner's own network that belongs to someone else; the owner must recognise the server's name shown after the probe, and the server proves it knew the code before the device signs anything |
| Skills (Agent Skills format) steer the agent | Only two things write a skill: the owner (edit or delete what exists, needs the right to change settings) and `skill.create` / `skill.update`, which always ask and show the full text first, so text the model took from a web page or file cannot become a standing instruction unseen. Folder names are the spec's `[a-z0-9-]`, never a path; files are atomic, capped (100 KB each, 500 KB together), only `references/` and `assets/` (no `scripts/`: nothing from a skill is executed), and links are refused. Only the SKILL.md (description and instructions) is given to the model as instructions, fenced in `<skill_instructions>` with its own closing tag removed from the text; it must fit on the approval card (7000 characters) so the owner reads all of it, and supporting files are shown on the card as far as there is room but come back to the model as untrusted data; it cannot grant permissions (`allowed-tools` is ignored, policy and approvals decide every action). A skill that does not follow the format is neither offered nor readable as instructions | An owner who approves a skill without reading it, or a device allowed to change settings, can still plant instructions that steer later tasks within what policy allows; the approval card shows the text but cannot judge it |
| Malicious dependency | Node agent core: zero runtime dependencies, two dev dependencies. Kotlin UIs: Kotlin/Compose/Ktor/coroutines/serialization from Maven Central, Gradle wrapper pinned by SHA-256, Yarn lockfile for the web build committed | Supply chain of those libraries; the UI side is NOT dependency-free |
| Model claims false success | Verification against files/HTTP; model-proposed criteria are labelled weaker than user-supplied ones | A badly chosen criterion can pass while the real goal is unmet |

| A skill from outside (GitHub, a folder, a cloned repository) steers the agent or runs code (D20) | A skill is given to the model only if `skills-lock.json` (config folder, outside every workspace) holds the hash of its exact content and it is switched on; a skill that only appears in a folder is `untracked`, one edited after approval is `modified`, neither is offered or readable. Installing, trusting and updating need an admin device and show the whole SKILL.md and every script first. Only `codeload.github.com` over HTTPS is contacted, no tokens, 10 MB packed / 25 MB unpacked / 1000 files; links and paths that leave the folder are dropped; the same name is never overwritten silently. Scripts run only through `skill.run`, after approval each time showing the script and how much holds it back, from a copy of the approved bytes in a fresh scratch folder: in Docker (no network, read-only root) by default, or on the computer (D21: JavaScript under Node's permission model, a safety net and not a boundary against hostile code, with the network open; Python and shell with no isolation, environment emptied, 60 s); the agent cannot add scripts or write to `.agents/`; trusting a skill needs the hash of what was shown; a change to a skill whose other files were altered is saved but not trusted | A skill the owner approved without reading it can still mislead the model within what the policy allows (it cannot widen approvals). A script's output is data. A Python or shell script run on the computer can do anything the owner can: the owner reading it is the only safeguard. A Node script can use the network. Docker escapes are out of scope; the image pull is network done by Docker. Hash checks cover the lock-recorded content, not what a remote repository does later |
| The agent running inside the phone app (D19) | Listens on `127.0.0.1` only. The one-time pairing code is written to a file in the app's private folder (mode 0600) and never to the log; only the app can read it. Pairing, signing and per-device rights are the same as for a computer | Other apps on a rooted phone, or a debugger, can read the app's private folder. The agent stops when Android stops the app (no foreground service yet) |

| Headlines of the feed mislead, or steer the model (D23) | Only `news.google.com` over HTTPS is contacted; the answer is size-capped and read as plain RSS; links must be https. Headlines are given to the model as data with its job fixed in the system text, and the model sees nothing else (no sources, links or workspace). Its answer is checked: no number that is not in the original, no question, shout or teaser, otherwise the original stays. Fixed rules drop clickbait and duplicates | A true-looking rewrite of a misleading headline is still misleading; the original is one tap away. The link goes to Google's redirect page, then the outlet |

Out of scope until later phases: cloud runtimes, memory poisoning, deploy credentials.
